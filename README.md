## 콘텐츠 관리

### CMS 관리자 화면

`/admin/`은 **블로그 글과 사진 전용**입니다. 구성원은 연구실 이야기·활동 기록을 작성하고 사진을 첨부해 검토를 요청합니다. 관리자는 같은 화면에서 수정 요청을 보내거나 **승인하고 반영**할 수 있습니다. 승인된 글과 사진은 한 번의 GitHub 커밋으로 `main`에 반영되고 기존 GitHub Actions가 홈페이지를 배포합니다.

구성원은 공용 `member` 아이디와 비밀번호, 본인은 별도 `admin` 아이디와 비밀번호로 로그인할 수 있습니다. 개인별 가입과 초대 메일 없이 시작하는 계정 생성 도구를 제공합니다. 공용 계정으로는 같은 작성·제출 내역을 공유합니다. 로그인과 검토 권한, 제출 자료는 Supabase에서 관리합니다. GitHub 토큰은 서버에만 보관하며, 구성원 계정으로는 게시 API를 호출해도 반영할 수 없습니다. 첫 설치 방법과 필요한 연결 설정은 [CMS 설치 안내](supabase/README.md)에 있습니다.

연결 설정 전에는 **화면 체험하기**로 작성자·관리자 역할을 바꿔 작성 → 제출 → 수정 요청 → 승인 흐름을 살펴볼 수 있습니다. 체험 데이터는 해당 브라우저에만 저장되며 실제 계정, 메일 발송, GitHub 커밋, 홈페이지 배포를 만들지 않습니다.

관리자는 기존 블로그 글을 검색하여 가져와 수정할 수 있습니다. 원래 글 주소와 사진은 보존합니다. 멤버·시설·논문·공지사항은 아래의 GitHub 파일에서 본인이 직접 관리합니다. CMS 화면과 서버 모두 다른 콘텐츠의 등록·수정·사진 첨부·게시를 차단하며, 이전 CMS 초안이 있어도 블로그 이외의 자료는 표시하거나 반영하지 않습니다. 승인 후에는 배포 시간이 조금 필요하므로 CMS의 반영 요청 상태와 실제 홈페이지 공개 시점을 구분해서 확인하세요.

### 사이트 점검 모드

`_config.yaml`에서 `maintenance: true`로 바꾸고 커밋·푸시하면, 배포 완료 후 홈·Team·개인 프로필·블로그 등 모든 HTML 페이지가 점검 안내로 바뀝니다. `maintenance_message`로 안내 문구를 수정할 수 있습니다.

다시 열 때는 `maintenance: false`로 바꿔 커밋·푸시하면 됩니다. 구성원과 게시글 데이터는 삭제되지 않습니다. 점검 화면에는 기존 페이지 본문과 메뉴를 출력하지 않으며, 자바스크립트가 꺼져 있어도 동일하게 표시합니다.

이 기능은 안내 화면 전환입니다. 사진 등 정적 파일의 직접 주소나 공개 GitHub 저장소까지 비공개로 바꾸지는 않습니다.

화면은 `_layouts`, `_includes`, `_styles`, `_scripts`의 자체 코드로 구성합니다. 별도 Jekyll 테마는 사용하지 않습니다. `Gemfile`과 `Gemfile.lock`은 콘텐츠 파일을 HTML로 변환하고 GitHub Pages에 배포하기 위한 빌드 의존성이므로 유지합니다. 활성 플러그인은 사이트맵 생성과 수정일 기록에 필요한 두 개입니다.

파일을 직접 관리할 수도 있습니다. Team·Blog·Notice는 Markdown 파일 하나가 항목 하나이며, Facility·Publication은 YAML 목록에서 관리합니다. 파일을 추가·수정한 뒤 GitHub에 반영하면 배포됩니다.

| 콘텐츠 | 관리 위치 | 자동 반영 |
| --- | --- | --- |
| Team | `_members/` | 기존 구성원 분류와 프로필 |
| Blog | `_blog/` | 연도별 목록, 개수, 상세 페이지, 이전·다음 글 |
| Notice | `_notice/` | 최신순 공지 목록, 상세 페이지, 이전·다음 글 |
| Facility | `_data/facility.yaml` | About의 장비 목록 |
| Publication | `_data/citations.yaml` | 국내외 논문·학위논문 분류와 연도별 목록 |

Blog는 기존 `_data/blog.yaml` 목록을 `_blog/` 글 파일로 옮겼습니다. 앞으로 목록 데이터를 따로 작성할 필요가 없습니다. 기존 사진 9개와 본문, 기존 글 주소는 유지했습니다. 사진 파일명에 있던 날짜를 각 활동 날짜로 사용했습니다.

### 글 추가하기

1. `content-templates/blog.md` 또는 `content-templates/notice.md`를 해당 폴더에 복사합니다.
2. 파일명을 `2026-09-27-activity-name.md`처럼 정합니다. 공개 후 파일명을 바꾸면 주소도 달라지므로 유지합니다.
3. 맨 위 `title`, `date`를 수정하고 `---` 아래에 본문을 씁니다. 목록은 `date`의 최신순입니다.
4. 사진을 `images/blog/연도/` 또는 `images/notice/`에 넣고 `image`에 경로를 적습니다. 대표사진은 목록(Blog), 상세 페이지, 공유 미리보기에 사용됩니다. 사진이 없으면 `image` 줄을 생략합니다.
5. 공개할 준비가 되면 `published: true`로 바꿉니다. `published: false`인 글은 배포에서 제외됩니다. 템플릿 안내 문구는 실제 본문으로 바꿔 주세요.

미래 날짜의 글도 해당 날짜 전에는 배포에서 제외됩니다. 날짜가 지난 뒤 GitHub Actions를 다시 실행하거나 변경 사항을 푸시해야 반영되며, 자동 예약 발행은 설정되어 있지 않습니다.

제목·날짜·사진만 있어도 Blog 항목을 만들 수 있고, 나중에 같은 파일에 본문을 추가하면 됩니다. `description`은 검색·공유 설명, `image_alt`는 대표사진 대체 텍스트, `image_caption`은 대표사진 아래 설명이며 모두 선택 사항입니다.

여러 사진을 추가할 때는 글 상단의 `---` 사이에 아래처럼 `gallery`를 넣습니다. Blog·Notice 모두 지원하며 사진은 본문 아래에 원본 비율로 표시됩니다.

```yaml
gallery:
  - image: images/blog/2026/photo-01.jpg
    caption: "첫 번째 사진 설명"
  - image: images/blog/2026/photo-02.jpg
    caption: "두 번째 사진 설명"
```

본문 중간에 사진을 넣으려면 `![사진 설명](/images/blog/2026/photo-01.jpg)`를 사용합니다.

### 논문 이미지

`_data/citations.yaml`의 `image`에 경로를 넣으면 가로형 로고와 세로형 표지 모두 같은 틀 안에 원본 비율을 유지하며 중앙 정렬됩니다. 새 이미지마다 CSS를 수정할 필요가 없습니다. 이미지 파일 자체에 포함된 여백은 보존됩니다.
